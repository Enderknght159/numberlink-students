Code walkthrough · Numberlink puzzle

One puzzle state, written four times

Python, C++, C# and Java versions of the same class: a single position in the search tree for a Numberlink board. It is not a game UI and not a solver — except the Java file, which adds DFS and BFS to actually finish the puzzle.

4 implementations 5 × 5 sample board state-space search no build files

01Four files, one design

All four files are the same object model translated literally: same fields, same method names, same order of operations. Reading one teaches you the other three. The only structural difference is where the actual solving lives.

The one idea to take away

The board arrays do two jobs at once. They store the puzzle, and they store which cells are already used. A path physically cannot cross itself or another pair, because every drawn cell becomes non-zero — the rule is enforced by the data structure, not by extra bookkeeping.

The hard-coded board used by every main. Grid is 5 × 5 = 25 cells, 10 of which are pre-printed endpoints, so every complete solution fills 15 empty cells and takes exactly 20 moves.

Pair 5 is nearly free: its cells sit two apart on the bottom row, so it costs exactly two moves. Pairs 1 and 3 run between mirrored corners, which is what makes this particular board take real search time.

03What a state holds

A state is not a solution. It is "the paths drawn so far, plus where the pencil currently is". Solutions are built one cell at a time.

The endpoint arrays are indexed by pair number and index 0 is never used — that keeps the code readable at the cost of one wasted slot. They are computed once in the first constructor and then shared by reference with every descendant state, which is the main memory optimisation in the design.

Step 1 matters: [row[:] for row in start_board] in Python, System.arraycopy in Java, Clone() in C#, and plain vector assignment in C++. Without it, painting a cell in a child state would corrupt the puzzle definition.

Step 4 is what makes a malformed board fail loudly instead of silently producing a search that can never succeed. It also rejects gaps in the numbering: a board containing only pairs 1 and 3 throws, because pair 2 appears zero times.

05The move engine

Three private pieces cooperate, and everything public is built on top of them.

Admission: canEnter

A cell may be entered only if it is empty, or if it is the end cell of the pair currently being drawn. Everything else — your own path, another pair's path, another pair's number — is blocked.

canEnter / _can_enterpython
# numberlink.py:92 — yes if the cell is empty, or if it is the end of the current pair
def _can_enter(self, row, col):
    if row == self.end_row[self.current_pair] and col == self.end_col[self.current_pair]:
        return True
    return self.board[row][col] == 0

Note the ordering: the endpoint check comes first. The end cell already holds a non-zero number, so without that first branch no path could ever finish.

Transition: stepTo

This is the state machine. If the target is the current pair's end cell, the pair closes: currentPair increments and the head jumps to the next pair's start cell. Otherwise the cell is painted and the head moves there.

stepTo / _step_topython
# numberlink.py:98 — put the head on (row, col); if it is the end, go to the next pair
def _step_to(self, row, col):
    if row == self.end_row[self.current_pair] and col == self.end_col[self.current_pair]:
        self.current_pair += 1
        if self.current_pair <= self.pairs_count:
            self.headrow = self.start_row[self.current_pair]
            self.headcol = self.start_col[self.current_pair]
    else:
        self.board[row][col] = self.current_pair
        self.headrow = row
        self.headcol = col

Two consequences fall out of this. The end cell is never re-painted, because it is already marked. And when the final pair closes, currentPair becomes pairsCount + 1 — the sentinel that every guard checks against.

Generation: four directions, one pattern

Each direction exists twice: a canMove… predicate and a move… performer. The performer is always the same three lines: copy, step, re-link.

public NumberLink moveUp() {
    if (!canMoveUp()) {

    NumberLink child = new NumberLink(this);
    child.stepTo(headrow - 1, headcol);

C++ — one shared helper for all four

NumberLink.cpp:70cpp
shared_ptr<NumberLink> makeChild(int row, int col) {
    auto child = make_shared<NumberLink>(*this);
    child->stepTo(row, col);
    child->g = g + 1;
    child->parent = shared_from_this();
    return child;
}

The copy-then-mutate pattern makes states externally immutable. There is no undo, no "restore the board" routine, and no risk of a failed move leaving a half-modified state — a failed move just returns the original object. The price is a full grid copy per move: O(rows × cols) time and memory, acceptable at this scale.

getNextStates() is the successor function the search consumes. The order is deliberately fixed — down, right, up, left — which is why DFS and BFS produce different but reproducible solution paths.

06Goal test

Two conditions, both required:

  1. currentPair > pairsCount — no half-drawn path remains.
  2. No 0 anywhere on the board — every cell used, which is the real Numberlink rule and why the goal test has to scan the whole grid after the last pair closes.

Because the check is cheap and the state is immutable, it is safe to call isGoal() repeatedly — which the search loops do.

07Equality & hashing

A search must recognise duplicates or it will expand the same position forever. Two states are equal only when all three of these match:

  • the board contents,
  • currentPair,
  • headrow / headcol.

The board alone is not enough. Two states can have identical painted cells while one is still mid-path and the other has moved on — the head's position and the active pair are what distinguish them.

They all follow the same contract: equal objects must hash equally, and unequal hash values are proof of inequality. The multiplier 31 is the conventional spread choice from Java's own String.hashCode.

08The search — Java only

Both solvers are the same twelve lines with a different container swapped in. That is the entire difference between depth-first and breadth-first here.

DFS — Stack (line 372)

Stack<NumberLink> stack = new Stack<>();
while (!stack.isEmpty()) {
    NumberLink current = stack.pop();
    if (current.isGoal()) return current;
    for (NumberLink next : current.getNextStates())
        if (visited.add(next)) stack.push(next);
}

BFS — Queue (line 400)

tkyeem1BFSjava
Queue<NumberLink> queue = new LinkedList<>();
while (!queue.isEmpty()) {
    NumberLink current = queue.poll();
    if (current.isGoal()) return current;
    for (NumberLink next : current.getNextStates())
        if (visited.add(next)) queue.add(next);
}

visited.add(next) doubles as the "is this new?" test, because Set.add returns false for an element already present. The short-circuit inside the if is therefore doing two jobs: dedup and admission control.

A subtlety worth knowing

On this puzzle every complete solution has the same length — 20 moves. The board must be full, each empty cell costs exactly one move, and each pair costs exactly one more to reach its end cell. So BFS's optimality guarantee buys nothing here: DFS returns a 20-move solution too. The real difference is memory and the order in which the tree is explored, not the answer's length.

Both check the goal when a state is removed from the container rather than when it is added. That is correct but slightly wasteful: the frontier can grow one full level deeper than necessary, and the start state gets re-tested although the constructor already handled the degenerate case.

09What each main does

Three of the four files are demonstrations, not solvers. They share the identical script and the identical hard-coded board:

  1. print the start state,
  2. print isGoal() — always false here,
  3. print every legal next state from the start,
  4. hand-draw pair 1 with the chained call right → right → down → down → left → down → down.

That chain only works because move… returns this on an illegal move instead of throwing — the calls never break a fluent chain.

The Java main replaces steps 3–4 with one call to tkyeem1BFS(start) and prints the full path to the solution via printPath().

10Findings

Ordered roughly by how much they matter. None of these stop the program from working.

No pruning of dead branches performance

Nothing detects that a drawn path just walled off a remaining endpoint. The search happily explores states that can never be completed. A cheap test — "does every unfinished pair's end cell still have at least one free neighbour?" — would cut the expanded state count dramatically, and it is the single highest-value change.

Name typo in the Java solver style

taqyeem1dfs versus tkyeem1BFS — two spellings of the same word, and inconsistent casing. Rename to solveDFS / solveBFS for symmetry.

Illegal moves return this risk

A failed move is invisible: the caller gets a state back and cannot tell it was rejected. Convenient for the demo chain, dangerous for a solver, because a forgotten can… check silently produces a duplicate state instead of an error.

C++ printPath() requires shared_from_this() risk

It throws if invoked on a stack-allocated state. Only safe on objects actually owned by a shared_ptr, as in main. Also not const, so it cannot be called on a const reference.

C# Equals ignores dimensions bug

It compares board[i, j] using this's rows and cols against other's array. Two differently sized states would throw an index error instead of returning false.

Python copy() copies the parent it is about to replace style

p.parent = self.parent is immediately overwritten by every move_* with child.parent = self. Harmless, but it reads as if the copy were going to share a parent, which it never does.

Full grid copy per move performance

Straightforward and bug-resistant, but O(rows × cols) per generated child. Fine for 5 × 5; at 10 × 10 with many pairs it becomes the bottleneck before the search itself does.

Scaling beyond the sample board needs two more things on top of pruning: a heuristic so the search can be guided (A* / IDA*) and a memoised impossibility check for partially drawn boards. The current design supports both without changing the state model.
